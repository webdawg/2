# Session log — 2026-08-03

Summary of the working session that produced this repo's initial state, for future reference.

## What this project is

A research prototype (see `SPEC.md` for the full spec) exploring whether a cluster of Rust
servers, each holding deterministic "defined datasets," can regenerate a target file from a
small transmitted "client file" (a sequence of `{dataset, coordinate, primer}` tuples) instead
of transmitting the file itself. The motivating use case: two supercomputers at opposite ends
of an extremely low-bandwidth, high-latency link (framed as an interplanetary/interstellar
scenario) where both ends are provisioned identically ahead of time, and only the tiny client
file crosses the link.

## Decisions made this session

- **Architecture**: documented in `SPEC.md` — terminology (defined dataset, coordinate,
  inference pad, primer, client file), the sender/receiver split, and the open questions
  (primer discovery method, client file encoding, dataset addressing). Client file encoding was
  explicitly deferred: it can't be designed on paper, it has to fall out of empirical results
  from a working bring-up + search prototype.
- **First bring-up step**: build a Rust TCP server (`server/` crate) that generates
  deterministic algorithmic data — three interchangeable generators selected by algorithm id:
  - `lcg` (id 0) — seeded linear congruential generator with O(log n) jump-ahead to a coordinate.
  - `hash-chain` (id 1) — SHA-256 hash chain; **no jump-ahead**, so reaching coordinate N costs
    O(N) chained hashes. This turned out to matter a lot (see Issues below).
  - `polynomial` (id 2) — raw quadratic formula `a*x^2 + b*x + c mod 256`, no PRNG/crypto.
  - Custom binary TCP protocol (`server/src/protocol.rs`): length-prefixed request
    `{algorithm_id, coordinate, length, params}` and response `{status, data|error}`.
- **Second bring-up step**: build a search/discovery client (`client/` crate) — the "sender"
  role from SPEC.md. Given a target byte sequence, it opens a TCP connection per algorithm and
  tries random `{coordinate, params}` combinations until it finds an exact byte-for-byte match
  or exhausts an attempt budget, reporting the best partial match either way.
- **License**: AGPL-3.0 chosen (over MIT/Apache-2.0/all-rights-reserved) — copyleft, so any
  modified version (including running it as a network service) must stay open under AGPL.

## Issues found and fixed

1. **Nagle's algorithm / delayed ACK**: request/response round trips were stalling ~40-80ms
   each over loopback. Fixed by setting `TCP_NODELAY` on both the server's accepted connections
   and the client's outbound connections.
2. **Hash-chain has no jump-ahead**: the search client originally picked a fully random `u64`
   coordinate for every algorithm. For hash-chain, a random coordinate near 2^64 requires
   computing on the order of 2^58 chained SHA-256 hashes before it can return — effectively
   hangs forever. Fixed by capping hash-chain's search coordinate range to
   `MAX_HASH_CHAIN_COORDINATE = 1_000_000` in the client (`client/src/main.rs`); left the
   full u64 range for `lcg`/`polynomial`, which have real jump-ahead.
3. Even bounded, hash-chain search is slow: each attempt recomputes its whole chain from
   scratch (no caching across attempts), so ~200,000 attempts at up to coordinate 1,000,000
   means billions of SHA-256 calls in an unoptimized debug build — estimated over an hour.
   This was flagged but not yet resolved before the session ended; options to revisit:
   lower the coordinate bound further, build with `--release`, or add chain-position caching
   across attempts within one search run.

## Empirical results so far (informal, small-scale)

- 1-byte targets: all three algorithms found an exact match in a few hundred attempts
  (consistent with the ~1/256 per-attempt match probability).
- 2-byte target (`"hi"`): `lcg` found a match after 6,299 attempts (expected ~65,536, but high
  variance makes this unsurprising); `hash-chain` and `polynomial` were still running / not yet
  confirmed when the session ended.
- No results yet for targets longer than 2 bytes — this is expected to hit the feasibility wall
  already flagged in `SPEC.md` (exact-match search cost grows exponentially with target length
  against structureless/random-like generators).
