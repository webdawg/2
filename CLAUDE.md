# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is a research prototype with three top-level docs that must stay aligned — read all three before
making design decisions here:

- `INTENT.md` — the *why*: the motivating thought experiment and the one hard information-theoretic
  constraint the design has to respect.
- `SPEC.md` — the *how*: terminology, architecture, and open technical questions.
- `COGNITION.md` — the *research methodology*: the empirical build-search-learn loop this project runs
  on, and a standing summary of what's been learned running it so far (individual session logs are
  `SESSION_<date>.md` at the repo root).

## Prerequisites

Rust toolchain (rustc + cargo). Not installed by default — on Arch/Manjaro:

```
sudo pacman -S rust
```

(or via `rustup` if you want per-project toolchain version management instead of the system package).
No other system dependencies; crate dependencies (e.g. `sha2`) are fetched automatically by cargo from
crates.io on first build.

## Commands

Run from the repository root (a Cargo workspace):

- Build: `cargo build`
- Test: `cargo test`
- Run a single test: `cargo test <test_name>` (e.g. `cargo test hash_chain_is_deterministic_and_matches_contiguous_read`)
- Run the server: `cargo run --bin server -- [port]` (default port `7878`, binds `127.0.0.1`)

## Architecture

Workspace with a single crate so far: `server/`.

- `server/src/protocol.rs` — the wire format for the custom TCP protocol. A `Request` is
  `{algorithm_id: u8, coordinate: u64, length: u32, params: Vec<u8>}`; a `Response` is either the
  generated bytes or an error string. Both are length-prefixed, big-endian, no external serialization
  crate. `read_request`/`read_response` and `Request::write_to`/`Response::write_to` are the only
  encode/decode entry points — reuse them rather than hand-rolling wire parsing elsewhere (e.g. in tests
  or future client code).
- `server/src/algorithms/` — the deterministic data generators, dispatched by `algorithm_id` in
  `algorithms::generate`. Each takes a `coordinate` (starting offset) and `length` (bytes to produce) and
  must return identical output for identical inputs — determinism here is the entire point of the
  project (see SPEC.md's "defined dataset" concept). Three algorithms currently:
  - `lcg.rs` (id `0`) — seeded linear congruential generator with closed-form jump-ahead (`advance`), so
    reaching a large coordinate is O(log n) rather than replaying the generator from zero.
  - `hash_chain.rs` (id `1`) — SHA-256 hash chain (`h_{n+1} = SHA256(h_n)`) treated as a virtual byte
    stream. Unlike the LCG, this has no jump-ahead: reaching a coordinate requires recomputing every
    block from 0, so it's O(coordinate) — a known limitation, fine for the current small-scale prototype
    only.
  - `polynomial.rs` (id `2`) — a raw quadratic formula (`a*x^2 + b*x + c mod 256`) with `a, b, c` as
    params; no crypto/PRNG involved, just arithmetic.
- `server/src/lib.rs` — connection handling (`run`, `handle_connection`): one thread per TCP connection,
  looping request→generate→response until the client disconnects.
- `server/src/main.rs` — thin CLI entry point (port arg, bind, call into `lib.rs`).
- `server/tests/determinism.rs` — integration tests that spin up a real server on an ephemeral port and
  connect real `TcpStream`s to it (not just unit-testing the generators directly), to verify determinism
  and correctness through the actual protocol, not just the underlying math.

This crate is one "server" in SPEC.md's terminology — it owns a coordinate range/dataset and answers
`{coordinate, primer}`-style requests. The higher-level pieces from SPEC.md (client file format, primer
discovery/search, cluster coordination across multiple servers) are not implemented yet.
